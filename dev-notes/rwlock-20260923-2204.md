# cooperative 异步读写锁：设计、决策与实现记录

- 日期：2026-09-23 22:04（2026-09-23 更新实现记录）
- 分支：`atomic_sync` @ `dev/0.3.0`
- 目标 crate：`atomic_sync`，新增路径 `rwlock::cooperative`
- 对端接口：`abs_sync` @ `dev/0.3.0` 的 `async_rwlock::TrAsyncRwLock`

本文记录从设计评审到落地实现的完整因果链：哪些设计被否决、为什么，
以及最终实现里每个不显然的取舍是怎么来的。

---

## 1. 目标与非目标

**目标**

- 实现 `TrAsyncRwLock` / `TrAsyncRwLockAcqSess` / 三个 Guard trait /
  `TrAsyncRwLockUpgradeSession` 的全部关联类型与生命周期约束；
- 运行时无关：只用 `core::task::Waker`，不引入任何异步运行时；
- `no_std` + `alloc`：等待节点、等待队列需要堆分配；
- 取消安全：`TrMayCancel` 语义下调用者可随时丢弃 future，锁状态必须自洽，
  且**不能因为取消而让其他等待者永久饥饿**。

**非目标**

- 不做毒化语义（`CoopRwLockError::Poisoned` 只是预留变体）；
- 不追求极致的无锁快速路径。

## 2. 与 `preemptive` 版本的关系

`rwlock::preemptive::SpinningRwLock` 提供了可直接对照的所有权骨架：

- `RwLockState`：把状态字拆成若干域，所有迁移都是"谓词 + 期望值"的比较交换；
- `AcqSession<'a>(&'a SpinningRwLock)`：会话只是锁的借用；
- `ReaderGuard/WriterGuard/UpgradableReaderGuard<'a,'g>(&'g mut AcqSession)`：
  Guard 借用会话，会话再触达数据；
- `TrShareMut` + `ManuallyDrop`：支撑 `self` 消费型的 `downgrade/upgrade`。

cooperative 版完全沿用这套所有权骨架，只把"自旋等待"换成"等待队列 + Waker"。

### 2.1 关于"升级为写者"的记账（一次被推翻的误判）

实现初期我曾判断 `preemptive` 的升级路径泄漏读者计数，理由是
`try_upgrade_upgradable_to_write` 只置 `WRITER_ACTIVE` 而不归还 `READER_COUNT`，
`on_writer_guard_drop` 也不减。**该判断是错的**，实测探针（已删除）显示：

```text
升级得到的写者还活着时           : reader_count == 1，写者置位
释放写者、但 UpgradeSession 仍活着 : reader_count == 1，try_write 仍然失败
释放 UpgradeSession 之后         : reader_count == 0，try_write 成功
```

也就是说：**可升级读那个"槽位"归 `UpgradeSession` 所有**，
写者只是"暂借"它。写者析构只清 `WRITER_ACTIVE`，
槽位由可升级读守卫析构时归还。这套记账是自洽的，不是缺陷。

cooperative 版因此**照搬**这套语义，而不是"修正"它：

```text
升级：  保留 UPGRADE_ACTIVE 与 READER_COUNT，仅置 WRITER_ACTIVE，
        并清除 UPGRADE_WAITING
释放写者：仅清 WRITER_ACTIVE
降级为可升级：清 WRITER_ACTIVE，置 UPGRADE_ACTIVE，R+1
```

这样 `UpgradeSession` 在升级成功后仍然可以再次 `try_upgrade` 或 `into_guard`，
写者侧也只有唯一一条释放路径，不需要任何"已消费"标记。

> 教训：判断"另一个实现有 bug"之前，先确认它把所有权记在谁头上。
> 探针测试的价值就在这里。

### 2.2 `preemptive` 真正的问题：升级可能被新读者无限推迟

`preemptive` 的升级条件是"`UPGRADE_ACTIVE` 且 `READER_COUNT == 1`"，
但升级等待期间并不阻止新读者进入，而新读者又会让 `READER_COUNT > 1`。
在持续有新读者的负载下，`upgrade` 可能**永远等不到独占**。

cooperative 版对此做了改进（见 §4.5）：一旦有升级请求挂起，
就置位 `UPGRADE_WAITING` 栅栏，读路径不再放行新读者。

## 3. 最终结构

```text
CooperativeRwLock<T: ?Sized, D, B, O>     // 栈上的外壳，内联持有资源
├── _pin_  : PhantomPinned
├── core_  : Arc<RwCore<D, B, O>>         // Sized 且与 T 无关
└── data_  : UnsafeCell<T>                // T: ?Sized 时是最后一个字段

RwCore<D, B, O>
├── stat_         : CoopRwState<D, B, O>      // 状态字（无锁快速路径）
├── queue_        : SpinLock<WaitQueue>       // FIFO 等待队列
└── upgrade_wait_ : SpinLock<Option<Waker>>   // 升级专用等待槽（不进 FIFO）

WaitQueue = VecDeque<Arc<WaitNode>>
WaitNode { kind: Read | UpgradableRead | Write, slots: SpinLock<Vec<WaiterSlot>> }
WaiterSlot { waker: Option<Waker>, state: Waiting | Acquired | Cancelled }

CooperativeAcqSession<'a, T, D, B, O>(&'a CooperativeRwLock<..>)
ReaderGuard / WriterGuard / UpgradableReaderGuard<'a,'g,..>(&'g mut CooperativeAcqSession)
Upgrade<'a,'g,..>(UpgradableReaderGuard<..>)          // upgrade_session() 的产物
```

### 3.1 为什么 `RwCore` 里没有资源指针

原始设计是"`RwCore` 只存一个指向资源的指针"。选定"资源内联在外壳里"之后，
外壳的最终地址在构造时不可知，指针只能惰性写入并每次 `acq_session` 重新发布；
而它其实**完全多余**：会话已经借用外壳（`&'a CooperativeRwLock`），
Guard 借用会话，`Guard → AcqSession → data_` 全程类型安全、零原子操作。
再存一份指针只会多出一条需要 `unsafe` 维护的失效风险。

原设计的目的（`RwCore` 不承载 `T`、保持 `Sized` 且小）在"不放指针"时同样成立，
而且更彻底：`RwCore` **完全不泛型于 `T`**。若将来需要把数据访问路径从会话里
摘出来（例如 Guard 不再借用会话），再引入指针不迟。

## 4. 关键机制

### 4.1 状态字（5 个域）

```text
bit N-1        WRITER_ACTIVE     写者持有
bit N-2        WAITER_QUEUED     等待队列非空
bit N-3        UPGRADE_ACTIVE    存在可升级读者
bit N-4        UPGRADE_WAITING   该可升级读者已挂起升级请求
bit [0, N-5]   READER_COUNT      读者计数（含可升级读者）
```

`WAITER_QUEUED` 由队列的"空 ↔ 非空"翻转维护，只在队列锁内更新；
快速路径靠它实现严格 FIFO：**队列非空即禁止插队**（写者不会饥饿）。

放行判定必须基于**同一份** `snapshot()`；快速路径可以绕过队列锁直接改状态字，
分多次读取会出现自相矛盾的判断。

### 4.2 等待节点：同质合并 + 逐等待者取消

读者合并进同一个节点（只有**队尾也是读节点**时才追加槽位，
否则会破坏 FIFO 次序）。每个槽位独立记录 waker 与状态，
因此单个读者取消只影响它自己的槽位。`pending_count() == 0`
（没有 `Waiting` 槽位）的队首节点会被剪掉。

节点槽位由自身的自旋锁保护，调用方总是**先持队列锁、再取节点锁**，
锁序固定，不会成环。

### 4.3 `pass()`：只唤醒，不分配许可

```text
pass():
  1. 从队首剪掉 pending_count()==0 的节点
  2. 队列已空 → 清 WAITER_QUEUED，返回
  3. 取状态快照：若 WRITER_ACTIVE 或 UPGRADE_WAITING → 谁都不放行
  4. 看队首 kind：
     - Read / UpgradableRead :
         依次唤醒队首连续的读类节点，遇到第一个 Write 节点停止；
         UpgradableRead 额外要求当前没有 UPGRADE_ACTIVE（全锁至多一个）
     - Write : 若 READER_COUNT==0 且没有 UPGRADE_ACTIVE → 唤醒它
```

被唤醒者随后在自己的 `poll` 里用一次 `Cmpxchg` 领取许可；
失败（条件被别人改变）就退回等待，接受少量虚假唤醒。
**许可从不预先分配**，所以"被唤醒后立刻取消"不会泄漏任何许可。

### 4.4 取消：必须主动撤销，并重跑 `pass()`

原始方案是"队列只存 `Weak<WaitNode>`，drop 什么都不做"。这有**活性漏洞**：

```text
写者释放 → pass() 唤醒队首读者 R1（此刻 R1 仍是 Waiting）
R1 的 future 在被 poll 之前被丢弃
→ 没人再唤醒 R1 后面的写者，而 R1 也永远不会来拿锁 → 写者永久饥饿
```

因此队列直接持 `Arc<WaitNode>`，future 的 `Drop` 在队列锁内
把槽位标为 `Cancelled` 并**重跑一次 `pass()`**。这样：
- 队首被取消了 → `pass()` 剪掉该节点并唤醒下一个；
- 取消的节点不在队首 → 它迟早会被剪掉，不阻塞任何人。
回归测试：`cancelled_head_waiter_should_not_starve_followers`。

### 4.5 升级：不进 FIFO 队列 + 升级栅栏

**为什么升级不能进队列**：可升级读者持有读名额，而排队的写者要等
`READER_COUNT == 0`。若把升级请求排在写者后面，两者互等 → 死锁：

```text
[写 W][升级 U]：W 等 R==0（U 占着一个读名额），U 等队首（被 W 挡住）→ 死锁
```

所以升级用 `RwCore` 里**单独的 waker 槽位**（全锁至多一个可升级读者，
故至多一个升级等待者）：

- `upgrade_or_wait`：先置 `UPGRADE_WAITING` 栅栏、登记 waker，**再**尝试升级。
  顺序不能反：先尝试失败、再登记 waker 的话，夹在中间的"读者释放并检查等待槽"
  会两头落空，造成丢唤醒。
- 各 `release_*` 更新状态后调用 `wake_upgrade_if_ready_()`：条件成立就取走 waker
  在锁外唤醒。
- 栅栏使新读者无法进入，因此读者计数只会减少，
  "检查到条件成立"之后升级必定成功，不会出现拿到 waker 却升不了级的空转。
- 取消（future 被丢弃）时清栅栏并重跑 `pass()`，避免把读者永远挡在栅栏外。

回归测试：`async_upgrade_should_set_barrier_and_wake_when_alone`、
`cancelled_upgrade_should_lift_barrier`。

### 4.6 锁内绝不调用 `Waker::wake`

自旋锁不可重入，而部分执行器会在当前线程内联 poll 被唤醒的任务，
那个任务 poll 时又来抢同一把锁 → 同线程自死锁。
因此所有自旋锁临界区只做"收集 waker"，解锁之后才逐一 `wake()`。
`upgrade_wait_` 与队列锁**从不同时持有**（先解锁一个再取另一个），避免锁序成环。

### 4.7 与 `TrMayCancel` 的对接

手写 future 只负责"入队 / 领取 / 注册 waker / Drop 出队"，
且这几步在**同一段队列锁临界区**内完成（这是不丢唤醒的根本原因）；
取消的竞速交给 `gen_mcf2` + `abs_sync::ok_or::XtOkOr`：

```rust
#[gen_may_cancel_future(ReadAcquire, pub)]
async fn read_acquire_async_(sess: &mut CooperativeAcqSession, cancel: C)
    -> Result<ReaderGuard, CoopRwLockError>
{
    let acq = ReadAcquireInner::new(sess);
    match cancel.cancellation().ok_or(acq).await {
        Result::Ok(_) => Result::Err(CoopRwLockError::Cancelled),
        Err(r) => r,
    }
}
```

注意两点：
- 匹配必须写 `Ok(_)` 而不是 `Ok(())`：`TrCancellationToken::Cancellation`
  的 `Output` 在 trait 上是未约束的关联类型，写 `()` 无法通过类型检查；
- 外层 future 被丢弃时，`OkOr` 会连同内层 `*AcquireInner` 一起析构，
  后者在 `Drop` 里完成出队，因此取消路径天然被覆盖。

## 5. 决策记录

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 资源 `T` 的归属 | 外壳内联 `UnsafeCell<T>` + `PhantomPinned`（见 §3.1） |
| Q2 | 队列的取消/回收 | `SpinLock<VecDeque<Arc<WaitNode>>>` + 槽位状态 + drop 主动撤销（§4.4） |
| Q3 | 等待节点粒度 | 同质合并：读者共用一个节点，节点内含多个 waker 槽位（§4.2） |
| Q4 | 并发控制 | 原子状态字 + 独立队列自旋锁；快速路径无锁 |
| Q5 | 公平性 | 严格 FIFO：队列非空即禁止插队 |
| Q6 | 错误与命名 | `CoopRwLockError { WouldBlock, Cancelled, Poisoned }`；`CooperativeRwLock` / `CooperativeAcqSession` |
| Q7 | 依赖 | 引入 `gen_mcf2`；`extern crate alloc` 无条件 |
| 追加 | 升级是否进 FIFO | **不进**；用专用等待槽 + `UPGRADE_WAITING` 栅栏（§4.5） |

## 6. 已验证内容

`cargo test`（38 个单元测试 + 4 个集成测试 + 3 个文档测试）、
`cargo clippy --all-targets -- -D warnings`、`cargo doc` 全部通过。

覆盖的关键场景：

- 状态字迁移（含升级记账、栅栏、降级路径）的单元测试；
- 非阻塞获取的 `WouldBlock` 与释放后恢复；
- 写者等待全部读者退出、严格 FIFO（读 A → 写 W → 读 B 的放行顺序）；
- **队首等待者被唤醒后立即取消**的活性回归；
- 取消令牌触发与取消后锁状态自洽；
- 异步升级的栅栏语义、唤醒时机与取消撤栏；
- 多线程（4 线程 × 200 次写）不丢更新。

## 7. 遗留与后续

1. `preemptive` 的升级饥饿（§2.2）仍然存在，若要对齐 cooperative 的行为，
   需要给 `SpinningRwLock` 也加一个等价的栅栏位；
2. `CoopRwLockError::Poisoned` 尚无产生路径；
3. 未来可考虑：把快速路径下沉为单次原子读（`reader_count` 只读观察）、
   为读多写少场景加入"读者批量放行"的启发式、以及 `T: ?Sized` 的
   内置构造入口（目前依赖 unsize 强制转换）。
