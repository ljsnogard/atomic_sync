# cooperative 异步读写锁：设计、决策与实现记录

- 日期：2026-09-23 22:04（同日更新：升级排队、测试改用真实运行时）
- 分支：`atomic_sync` @ `dev/0.3.0`
- 目标 crate：`atomic_sync`，新增路径 `rwlock::cooperative`
- 对端接口：`abs_sync` @ `dev/0.3.0` 的 `async_rwlock::TrAsyncRwLock`

本文记录从设计评审到落地实现的完整因果链：哪些设计被否决、为什么，
以及最终实现里每个不显然的取舍是怎么来的。文中有**两处自我更正**，
它们是理解当前实现的钥匙，已分别标注。

## 1. 目标与非目标

**目标**

- 实现 `TrAsyncRwLock` / `TrAsyncRwLockAcqSess` / 三个 Guard trait /
  `TrAsyncRwLockUpgradeSession` 的全部关联类型与生命周期约束；
- 运行时无关：只用 `core::task::Waker`，不引入任何异步运行时；
- `no_std` + `alloc`：等待节点、等待队列需要堆分配；
- 取消安全：`TrMayCancel` 语义下调用者可随时丢弃 future，锁状态必须自洽，
  且**不能因为取消而让其他等待者永久饥饿**；
- **可用于多线程执行器**：获取 future 必须满足 `Send`，能被 `tokio::spawn`。

**非目标**

- 不做毒化语义（`CoopRwLockError::Poisoned` 只是预留变体）；
- 不追求极致的无锁快速路径。

## 2. 与 `preemptive` 版本的关系

`rwlock::preemptive::SpinningRwLock` 提供了可直接对照的所有权骨架：

- `RwLockState`：把状态字拆成若干域，所有迁移都是"谓词 + 期望值"的比较交换；
- `AcqSession<'a>(&'a SpinningRwLock)`：会话只是锁的借用；
- `ReaderGuard/WriterGuard/UpgradableReaderGuard<'a,'g>(&'g mut AcqSession)`：
  Guard 借用会话，会话再触达数据；
- `TrShareMut` + `ManuallyDrop`：支撑 `self` 消费型的 `downgrade/upgrade`。

cooperative 版完全沿用这套所有权骨架，只把"自旋等待"换成"等待队列 + Waker"。

### 2.1 更正一：`preemptive` 的升级记账**没有**泄漏

实现初期我曾判断 `preemptive` 的升级路径泄漏读者计数，理由是
`try_upgrade_upgradable_to_write` 只置 `WRITER_ACTIVE` 而不归还 `READER_COUNT`。
**该判断是错的**。实测探针（已删除）显示：

```text
升级得到的写者还活着             : reader_count == 1，写者置位
释放写者、但 UpgradeSession 仍活着 : reader_count == 1，try_write 仍然失败
释放 UpgradeSession 之后          : reader_count == 0，try_write 成功
```

也就是说：**可升级读那个"槽位"归 `UpgradeSession` 所有**，写者只是"暂借"它；
写者析构只清 `WRITER_ACTIVE`，槽位由可升级读守卫析构时归还。这套记账自洽，
cooperative 版因此**照搬**，不做"修正"：

```text
升级：      保留 UPGRADE_ACTIVE 与 READER_COUNT，仅置 WRITER_ACTIVE
释放写者：  仅清 WRITER_ACTIVE
降级为可升级：清 WRITER_ACTIVE，置 UPGRADE_ACTIVE，R+1
```

由此还免费获得一条语义（用户点名要的）：**写者守卫释放后会"回退"成原本的
可升级读**——`UpgradeSession` 可以再升级一次、`try_upgrade`，或者 `into_guard`
取回守卫。

> 教训：判断"另一个实现有 bug"之前，先确认它把所有权记在谁头上。

## 3. 最终结构

```text
CooperativeRwLock<T: ?Sized, D, B, O>     // 栈上的外壳，内联持有资源
├── _pin_  : PhantomPinned
├── core_  : Arc<RwCore<D, B, O>>         // Sized 且与 T 无关
└── data_  : UnsafeCell<T>                // T: ?Sized 时是最后一个字段

RwCore<D, B, O>
├── stat_  : CoopRwState<D, B, O>         // 状态字（无锁快速路径）
└── queue_ : SpinLock<WaitQueue>          // FIFO 等待队列

WaitQueue = VecDeque<Arc<WaitNode>>
WaitNode  = 读类节点（Read / UpgradableRead 槽位，可同质合并）
          | 独占节点（Write / Upgrade，各一个槽位）
WaiterSlot { kind, waker: Option<Waker>, state: Waiting | Acquired | Cancelled }

CooperativeAcqSession<'a, T, D, B, O>(&'a CooperativeRwLock<..>)
ReaderGuard / WriterGuard / UpgradableReaderGuard<'a,'g,..>(&'g mut CooperativeAcqSession)
Upgrade<'a,'g,..>(UpgradableReaderGuard<..>)          // upgrade_session() 的产物
ReadAcquire / WriteAcquire / UpgradableReadAcquire / UpgradeAcquire
                                                      // 获取 future（自带 TrMayCancel）
```

### 3.1 为什么 `RwCore` 里没有资源指针

原始设计是"`RwCore` 只存一个指向资源的指针"。选定"资源内联在外壳里"之后，
外壳的最终地址在构造时不可知，指针只能惰性写入并每次 `acq_session` 重新发布；
而它其实**完全多余**：会话已经借用外壳（`&'a CooperativeRwLock`），
Guard 借用会话，`Guard → AcqSession → data_` 全程类型安全、零原子操作。

原设计的目的（`RwCore` 不承载 `T`、保持 `Sized` 且小）在不放指针时同样成立，
而且更彻底：`RwCore` **完全不泛型于 `T`**。

## 4. 关键机制

### 4.1 状态字（4 个域）

```text
bit N-1        WRITER_ACTIVE   写者持有
bit N-2        WAITER_QUEUED   等待队列非空
bit N-3        UPGRADE_ACTIVE  存在可升级读者
bit [0, N-4]   READER_COUNT    读者计数（含可升级读者）
```

`WAITER_QUEUED` 由队列的"空 ↔ 非空"翻转维护，只在队列锁内更新；
快速路径靠它实现严格 FIFO：**队列非空即禁止插队**。

放行判定必须基于**同一份** `snapshot()`；快速路径可以绕过队列锁直接改状态字，
分多次读取会得到自相矛盾的判断。

### 4.2 等待节点：读类合并 + 逐等待者取消

- **读类节点**承载若干 `Read` / `UpgradableRead` 槽位：新到的读类等待者只在
  **队尾也是读类节点**时才合并进去（否则会破坏 FIFO 次序）。它们共享同一个
  排队位置，`pass()` 一次放行整组；
- **独占节点**（`Write` / `Upgrade`）只有一个槽位；
- 每个槽位独立记录 waker 与状态，单个等待者取消只影响它自己的槽位；
- `pending_count() == 0` 的队首节点会被剪掉。

节点槽位由自身的自旋锁保护，调用方总是**先持队列锁、再取节点锁**，锁序固定。

### 4.3 `pass()`：只看队首，只唤醒不分配

```text
pass():
  1. 从队首剪掉 pending_count()==0 的节点
  2. 队列已空 → 清 WAITER_QUEUED，返回
  3. 取状态快照：写者持有 → 谁都不放行
  4. 看队首节点（它领取完之前始终是后面的屏障，所以不必往后看）：
     - 读类节点：放行其中的 Read 槽位；
       UpgradableRead 槽位额外要求当前没有别的可升级读者（全锁至多一个）
     - Write   ：READER_COUNT==0 且无可升级读者 → 放行
     - Upgrade ：READER_COUNT==1（只剩它自己）→ 放行
```

被唤醒者随后在自己的 `poll` 里用一次 `Cmpxchg` 领取许可；失败就退回等待，
接受少量虚假唤醒。**许可从不预先分配**，所以"被唤醒后立刻取消"不会泄漏许可。

### 4.4 取消：必须主动撤销，并重跑 `pass()`

原始方案是"队列只存 `Weak<WaitNode>`，drop 什么都不做"。这有**活性漏洞**：

```text
写者释放 → pass() 唤醒队首读者 R1（此刻 R1 仍是 Waiting）
R1 的 future 在被 poll 之前被丢弃
→ 没人再唤醒 R1 后面的写者，而 R1 也永远不会来拿锁 → 写者永久饥饿
```

因此队列直接持 `Arc<WaitNode>`，future 的 `Drop` 在队列锁内把槽位标为
`Cancelled` 并**重跑一次 `pass()`**。回归测试
`cancelled_head_waiter_should_not_starve_followers`（用 compio 的
`JoinHandle::drop` 真正取消一个任务）。

### 4.5 升级请求进入队列，并插到队首

**更正二**：我最初把升级做成"队列之外的独立等待槽 + 状态字栅栏位"，理由是
"升级要被新读者饿死"。这在 cooperative 里是**多余的**：升级请求一旦入队，
`WAITER_QUEUED` 就已经挡住新读者（严格 FIFO）。真正需要解决的是别的问题——
**升级请求不能排在写者后面**：

```text
[写 W][升级 U] → W 等 READER_COUNT==0（U 占着一个读名额），
                 U 等队首（被 W 挡住）→ 死锁
```

所以升级请求**插到队首**：可升级读者此刻是持有者，它的"位置"本来就在所有
排队者之前，升级请求跟着它排在前面才是正确顺序。于是：

- 不会死锁：升级排在任何排队写者之前；
- 不会被新读者推迟：队列非空 → 快速路径拒绝新读者；
- 不需要额外的状态位，也不需要第二个自旋锁。

回归测试 `upgrade_should_jump_ahead_of_queued_writer`。

### 4.6 锁内绝不调用 `Waker::wake`

自旋锁不可重入，而部分执行器会在当前线程内联 poll 被唤醒的任务，
那个任务 poll 时又来抢同一把锁 → 同线程自死锁。
因此所有自旋锁临界区只做"收集 waker"，解锁之后才逐一 `wake()`。

### 4.7 更正三：形状照抄 `gen_mcf2`，实现必须手写

按决策引入 `gen_mcf2` 生成"`TrMayCancel` + `IntoFuture`"样板后，实测发现它生成的
future **无法被 spawn 到多线程执行器**：

```rust
tokio::spawn(async move {
    let mut s = lock.acquire_session();
    let w = s.write_async().await.unwrap();   // 编译错误：lifetime bound not satisfied
});
```

原因是宏生成的结构里存着一个不透明类型
`<() as Tr...Factory<..>>::MadeFuture`（`impl Future`）；
要证明外层 future 满足 `Send`，就得对任意生命周期证明该不透明类型 `Send`，
撞上 rust#100013（higher-ranked lifetime error）。把内部换成手写的**具体类型**
后，`Send` 按字段结构自然推导，`tokio::spawn` 直接通过。

结论：**保留 `gen_mcf2` 的命名与两件套形状，但手写实现**——
`XxxAsync`（`read_async()` 等的返回值）+ `XxxFuture`（真正的 future）：

```rust
pub struct ReadAcquireAsync<'a, 'g, T, D, B, O> { sess_: &'g mut CooperativeAcqSession<..> }

#[pin_project]
pub struct ReadAcquireFuture<'a, 'g, T, D, B, O, C = NonCancellableToken> {
    inner_: Option<ReadAcquireInner<'a, 'g, T, D, B, O>>,   // 具体类型：入队/领取/注册 waker
    #[pin] cancel_: Option<C::Cancellation>,
}
```

- `impl IntoFuture for XxxAsync`（返回不可取消的 `XxxFuture<.., NonCancellableToken>`）
  与 `impl TrMayCancel<'f> for XxxAsync`（返回 `XxxFuture<.., C>`）手写；
- `XxxFuture` 自身的 `IntoFuture` 由标准库 blanket impl 提供；
- `.may_cancel_with(token)` 只换 `cancel_` 字段，两件套之间通过构造函数转换；
- `poll` 先轮询取消，再轮询获取；任一侧就绪就清空两个字段
  （保持"完成后再 poll 即 panic"的约定）；
- 取消时直接丢弃 `inner_`，由它的 `Drop` 完成出队。

`pin-project` 用于结构体投影，避免手写 `unsafe`（`C::Cancellation` 未必 `Unpin`）。
`gen_mcf2` 依赖已移除。

### 4.8 更正四：状态迁移绝不能写在 `debug_assert!` 里（release 专属 bug）

性能测试第一次跑起来就卡死了，而**所有 debug 测试都是绿的**。定位结果：

```rust
pub(super) fn release_reader(&self) {
    debug_assert!(self.stat_.release_reader());   // ← release 下整句被丢
    self.run_pass_();
}
```

`debug_assert!(expr)` 在 `debug_assertions = false` 时**不会求值 `expr`**，
于是 release 构建里"释放/降级"的状态迁移根本没执行：读者计数只增不减，
升级永远等不到 `READER_COUNT == 1`，`upgrade_async` 就此永久挂起。

修正是把迁移无条件执行，断言只用来检查结果：

```rust
let _ok = self.stat_.release_reader();
debug_assert!(_ok, "state transition `release_reader` failed");
self.run_pass_();
```

**教训有两条**：

1. 任何有副作用的表达式都不能放进 `assert!`/`debug_assert!`；
2. 只跑 debug 测试会漏掉这一类 bug——本仓库因此把
   `cargo test --release` 也纳入验证清单（见 §6）。

### 4.9 更正五：槽位放行必须"一次性"，且不能过滤自己的唤醒

性能测试显示 8 线程下 `wake/op = 7.28`——每次操作触发 7 次跨线程唤醒。
根因是 `pass_` 的实现：它每次都把队首节点里**所有** `Waiting` 槽位的 waker
克隆出来重新唤醒，而一个槽位在等待者自己重新 poll 之前始终是 `Waiting`。
于是同一个等待者被反复唤醒、重新调度、再次 park，wake 次数被放大成倍。

修正：给槽位加 `Admitted` 状态。

- `pass_` 只放行 `Waiting` 槽位，放行时把 waker **取走**并转入 `Admitted`；
  同一个槽位在它自己重新挂起（`set_waker`，会把它置回 `Waiting`）之前
  不会再被放行；
- `pending_count` 把 `Waiting` 与 `Admitted` 都算作"未出结果"，
  因此队首节点仍然是后面等待者的屏障（FIFO 语义不变）。

效果（读多写少，8 线程）：`wake/op` 7.28 → 0.68，ns/op 1857 → 1007。

**但这次改动立刻让两个多线程压力测试挂死**，暴露出配套的一个坑：
原先为了少一次"自我唤醒"，`wake_wakers_` 会用 `will_wake` 把**自己的 waker**
过滤掉。在"一次性放行"语义下这是致命的——

```text
本线程在队列锁内放行了自己的槽位（waker 已被取走，槽位转为 Admitted）
→ 收集到的 waker 正是自己的
→ 因为"目的就是自己"而被过滤掉，不唤醒
→ 槽位已是 Admitted，之后任何一次 pass_ 都不会再放行它
→ 没有任何人能再唤醒它 → 永久挂起
```

修正：**不再过滤自己的 waker**。多一次自我唤醒最多多一次 poll，
代价远小于丢失唤醒；而"放行时先取走 waker"已经保证了不会出现唤醒风暴。

## 5. 决策记录

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 资源 `T` 的归属 | 外壳内联 `UnsafeCell<T>` + `PhantomPinned`（见 §3.1） |
| Q2 | 队列的取消/回收 | `SpinLock<VecDeque<Arc<WaitNode>>>` + 槽位状态 + drop 主动撤销（§4.4） |

| Q5 | 公平性 | 严格 FIFO：队列非空即禁止插队 |

| Q7 | 异步样板 | 命名与形状沿用 `gen_mcf2`（`XxxAsync` + `XxxFuture`），但**实现手写**（§4.7） |
| Q8 | 升级请求排队策略 | **进队列并插到队首**（§4.5），不使用队列外的等待槽 |

### 6.2 性能测试（`benches/rwlock_cooperative.rs`）

方法：用带种子的伪随机序列为每个竞争者生成操作脚本（读 / 写 /
可升级读→升级→降级 / 让出执行权），N 个竞争者各跑一份，扫描 N = 1/2/4/8，
报告每次操作的纳秒数、相对对照的比值，以及相对 N=1 的扩展比。

对照组与理由：

- `tokio::sync::RwLock`：同为异步读写锁，是最直接的对照；
  它没有"可升级读"，脚本里的升级操作在它这侧退化为 `write()`；
- `std::sync::RwLock`：只放在"N 个 OS 线程"一节，说明线程模型差异，
  **不是同类对照**（我方用 `block_on` 驱动，对方是阻塞 API）；
- compio 没有自带 `RwLock`，但它那一节仍用 `tokio::sync::RwLock` 对照
  （tokio 的锁不依赖 tokio 运行时）。

规模可用环境变量调整（`RWLOCK_BENCH_OPS` / `RWLOCK_BENCH_ROUNDS` /
`RWLOCK_BENCH_COMPETITORS` / `RWLOCK_BENCH_HOLD`）。

#### 实测（4 核机器，每竞争者 20000 次操作，取 3 轮最好）

读多写少（读 75% / 写 15% / 升级 5% / 让出 5%），ns/op：

结论与解读：

- **无竞争路径优于对照**（N=1 快 1.1~1.4 倍），来自 §4.3 的"快速路径只做一次 CAS"
  与 `run_pass_` 在无人排队时不碰队列锁；
- **单线程执行器下全面占优**（N=8 读多写少 57 vs 82），且竞争者越多单次开销越低：
  等待者被唤醒后是同一线程上的顺序执行，没有跨线程调度成本；
- **多线程真实竞争下落后**（N=8 读多写少 610 vs 421）。定位见 §6.3：
  主因是"队列非空即禁止读者插队"这条严格 FIFO 规则把 88% 的操作赶进队列；
- **OS 线程一节最能说明"线程模型"的差别**：同为线程阻塞/自旋，
  `preemptive`（自旋 + yield）从 76 → 108 ns/op 几乎不退化，`std::RwLock`
  从 72 → 116 也稳定，而 cooperative 用 `block_on` 驱动时从 63 → **16332**。
  原因是 `block_on` 每次等待都要 park/unpark（一次 futex 往返），
  在短临界区下这个固定成本远超真正的锁开销。**这一节不是同类对照**：
  把异步锁强行用阻塞驱动本就不是它的使用场景。

2. `pass_` 只在状态确实可能放行时才跑（例如缓存"队首类型"作为提示），
   减少队列锁争用——N=8 时仍有 `pass/op ≈ 2.7`；
3. 批量放行连续的读类节点，减少"一个节点一次交接"的往返；
4. **重新审视公平性策略**：严格 FIFO 在 8 线程下把读多写少负载拖慢约 3 倍
   （§6.3 第 5 步）。折中方案已单独成文：

### 6.3 "8 线程性能崩塌"的定位过程

原始现象（读多写少，tokio 多线程，ns/op）：N=1 **66**、N=2 223、
N=4 73、N=8 **1387**（比 tokio 慢 4 倍、比自身 N=1 慢 21 倍）。

判断链条与每一步的证据：

1. **排除"算法成本"**：同一份负载、同一个锁，compio 单线程 N=8 只要
   `81 ns/op`。单线程下等待的代价只是"把任务标为就绪"，说明每次操作的
   锁内工作量没问题，问题在**交接（handoff）**。
2. **排除"纯读也没救"**：把负载换成纯读（95% 读、0 写/升级）后，
   N=8 回到 `119.9 ns/op`，且计数器显示 `入队/op = 0, pass/op = 0,
   wake/op = 0`。→ 崩塌只发生在**排队路径**上，即写者/升级需要排他时。
3. **定位到唤醒次数**：混合负载加计数器后，N=8 时
   `入队/op = 0.83`、`pass/op = 2.36`、而 `wake/op = 7.28`。
   每次跨线程唤醒要经历 "wake → 任务被别的 worker 调度 → 重新 poll"，
   在 4 核上被 8 个线程抢 CPU 时单价约 200ns 量级，7.3 × 200ns ≈ 1.5µs，
   与实测 1.86µs 吻合。→ §4.9 的"一次性放行"修复，`wake/op` 降到 0.68。
4. **剩余部分归因于公平性策略**：修完仍差 9 倍，此时 `快路/op` 只有 0.008
   ——**快速路径几乎全废**。原因是为了"写者不饥饿"选的严格 FIFO：
   只要队列非空，新读者就一律被 `WAITER_QUEUED` 拒绝，于是"有一个等待者"
   就被放大成"所有读者都要排队"：每个读操作都要分配节点、抢队列锁、
   注册 waker，再等一次跨线程唤醒。
5. **对照实验确认**：临时去掉读快速路径里的 `WAITER_QUEUED` 检查
   （允许读者在无写者时插队），N=8 立刻从 `1007 → 334 ns/op`，
   `快路/op` 0.008 → 0.754、`入队/op` 0.94 → 0.20。
   → **这就是严格 FIFO 的代价**（该实验已回退，策略维持你原来的选择）。

修完两条（§4.9 的一次性放行 + 不过滤自我唤醒）后的当前数字：

| 竞争数 | 修复前 | 修复后 | tokio::RwLock | 相对对照 |
|---|---|---|---|---|
| 1 | 66.8 | **66.8** | 91.4 | 1.37x |
| 2 | 223 | 202.4 | 186.4 | 0.92x |
| 4 | 73 | 76.3 | 200.9 | 2.63x |
| 8 | 1857 | **609.7** | 497.2 | 0.82x |

（N=8 从"慢 4 倍"变成"基本持平"；若愿意放弃写者公平性，按第 5 步的实验
可以进一步降到 ~334ns/op。）

### 6.4 竞争者数/工作线程数不匹配时的性能形状（结论：不是 bug）

现象：tokio 多线程一节里 N=2 比 N=1 与 N=4 都差，N=4 甚至接近单线程。

**先修指标口径**：`ns/op = 总耗时 /(N × ops)` 是**聚合吞吐**口径。当负载被
排他操作（写/升级，约占 20%）串行化时，总耗时几乎不随 N 变化，
`ns/op` 就会随 `1/N` 下降，于是"N 越大越快"是一种错觉。bench 因此增加了
**整轮总耗时（= 每个竞争者跑完自己那份脚本要多久）** 一列。

加入该列后的矩阵（读多写少，每竞争者 10000 次操作，3 轮取最好）：

| 任务数 | worker 数 | cooperative ns/op | 整轮总耗时 | 每任务耗时（相对单任务 0.73ms） |
|---|---|---|---|---|
| 1 | 1 | 73.3 | 0.733 ms | 1.0x |
| 2 | 2 | 218.2 | 4.365 ms | **6.0x** |
| 2 | 4 | 68.5 | 1.370 ms | 1.9x |
| 4 | 2 | 1136.6 | 45.466 ms | 62x |
| 4 | 4 | 71.6 | 2.863 ms | 3.9x |
| 8 | 8 | 541.9 | 43.352 ms | 59x |

重复性（每配置跑 3 次，以上均为 `best_of(3)`，仍能看出稳定趋势）：

| 配置 | 三次的每任务耗时 |
|---|---|
| 2 任务 / 2 worker | 4.49 / 4.15 / 3.99 ms（稳定地差） |
| 4 任务 / 4 worker | 3.52 / 3.58 / 2.71 ms |
| 2 任务 / 4 worker | 1.55 / 1.33 / 3.20 ms（通常最好，方差偏大） |

三条判据说明**这既不是我们的锁的 bug，也不是 tokio 的**：

1. **对照组同形**：`tokio::sync::RwLock` 在同样配置下也是 N=2 比 N=1、N=4 差
   （2/2 = 180 vs 1/1 = 94.7），而且它在 4/4 也没有回到单线程水平；
2. **多给一个空闲 worker 就能治好**：任务数仍是 2，但 worker 从 2 提到 4，
   每任务耗时从 4.2ms 降到 1.3~3.2ms。锁的 bug 不会因为"多几个空闲线程"而消失，
   而"唤醒后要等有空闲 worker/CPU 才被调度"会；
3. **去掉升级操作后我们的异常完全消失**：把负载换成"读 70 / 写 25 / 升级 0"后，
   2/2 变成 71.6 ns/op，比 N=1 的 89.7 还好。说明我们这一侧的放大来自升级路径
   （它要求可升级读者独占，请求插队期间还挡住新读者）；tokio 没有升级语义
   （脚本里退化为 `write()`），所以它那一侧来自纯读写竞争。

机制：**交接（handoff）要等调度**。等待者被唤醒后必须等到一个空闲 worker
（以及 CPU）才能重新 poll 并领取许可。三条推论都能对上：

- `workers < tasks` 是灾难（4/2：45ms）：被唤醒的任务得**抢占**另一个正在跑的任务，
  一次交接要等一个时间片；
- `workers > tasks` 最健康（2/4）：总有空闲 worker 立即接手；
- `workers == tasks` 处在中间，且唤醒是"叫醒一个刚睡下的线程"，
  因此对小 N 特别敏感——这也是 N=2 抖动的来源。

尚未验证的一条次要机制：为什么 4/4 的每任务耗时（~3ms）系统性地优于 2/2（~4.2ms）。
领先假设是**批量放行的摊薄效应**——任务多的时候，一次排他段结束时队首读节点里
往往已合并了多个读者，`pass_` 一次唤醒就放行整组，一次交接服务多个操作；
2 个任务时每次交接只服务 1 个操作。验证方法是给 `pass_` 加"每次放行唤醒的槽位数"
计数器，在 2/2 与 4/4 下对比（可与公平性改造一起做）。

**对 `benches/mutex_contention.rs` 的启示**：那里也有 `THREADS` 从 3 到 8 的扫描，
同样应当报告"每任务耗时"而不是只看聚合值，否则容易误读。

## 7. 遗留与后续

1. `CoopRwLockError::Poisoned` 尚无产生路径；
2. `T: ?Sized` 目前只能靠 unsize 强制转换构造，没有内置入口；
3. `pass()` 当前只处理队首节点；未来可考虑一次放行多个连续读类节点，
   或为读多写少场景加入批量放行启发式；
4. 严格 FIFO 是"写者不饥饿"的代价：只要有等待者，新读者就走不进快速路径。
   若实测在纯读多写少场景下代价偏高，可以考虑允许读者插队（会牺牲写者公平性）。

> 注：`rwlock::preemptive` 版本的升级饥饿问题不在本轮范围内（该实现本身
> 定位为演示/不实用），因此不做对齐。
